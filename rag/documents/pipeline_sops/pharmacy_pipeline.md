# Pharmacy Data Quality Pipeline SOP

## 1. Purpose

This document defines the standard processing flow for Pharmacy data within the Healthcare Data Quality and Anomaly Detection Platform.

The pipeline identifies Pharmacy data, validates its structure, applies Pharmacy-specific rules, evaluates anomalies using ML and rule-based detection, and produces structured evidence for downstream risk assessment and RAG.

---

## 2. Pipeline Flow

Pharmacy Data
    ↓
Input Identification
    ↓
Schema Validation
    ↓
Pharmacy-Specific Rules
    ↓
Pharmacy ML Model
    ↓
Anomaly Detection
    ├── Rule-Based Detection
    └── ML-Based Detection
    ↓
Anomaly Correlation
    ↓
Risk / Severity Assessment
    ↓
SLA Risk
    ↓
RAG Input
    ↓
RCA + Recommendation

---

## 3. Input Identification

The system identifies whether the incoming dataset belongs to the Pharmacy domain.

Identification may use:

- Source
- Dataset type
- File type
- Schema
- Field names
- Dataset metadata

The identified Pharmacy dataset is routed to the Pharmacy processing pipeline.

---

## 4. Schema Validation

The Pharmacy dataset is validated against the expected Pharmacy schema.

Validation may include:

- Required fields
- Data types
- Field names
- Date formats
- Numeric values
- Nullability
- Allowed categorical values
- Duplicate identifiers
- Schema compatibility

Schema violations are captured as structured evidence.

---

## 5. Pharmacy-Specific Validation

Pharmacy-specific rules are applied after schema validation.

Examples include:

- Invalid NDC information
- Invalid provider identifiers
- Invalid fill dates
- Invalid prescription dates
- Invalid days supply
- Invalid quantity
- Invalid pharmacy identifiers
- Invalid claim status
- Duplicate prescription records
- Duplicate pharmacy transactions
- Invalid refill information
- Missing required pharmacy fields
- Inconsistent prescription information
- Unexpected processing delays

Each rule violation should provide structured evidence.

---

## 6. Pharmacy ML Model

The Pharmacy ML model identifies unusual patterns in Pharmacy data.

Relevant ML output may include:

- Model name
- Anomaly score
- Contributing features
- Observed values
- Expected values or ranges
- Deviation information
- Record identifier

The ML model identifies anomalous behavior.

The ML model does not independently determine the final root cause or remediation.

---

## 7. Anomaly Detection

Pharmacy anomalies are detected using:

### Rule-Based Detection

Identifies explicit violations of Pharmacy data-quality rules.

### ML-Based Detection

Identifies statistical or behavioral deviations.

Both sources are combined into the anomaly representation.

---

## 8. Anomaly Correlation

Related Pharmacy anomalies are correlated to identify potentially common underlying problems.

Correlation may consider:

- Record
- Field
- Pharmacy
- Provider
- Rule
- ML feature
- Time period
- Anomaly pattern

The objective is to identify relationships between multiple anomaly signals.

---

## 9. Risk and Severity

The correlated anomalies are evaluated for operational impact.

Potential factors include:

- Severity
- Number of affected records
- Frequency
- Data-quality impact
- Processing impact
- SLA exposure

The resulting risk/severity information is passed to the next stage.

---

## 10. SLA Risk

The system determines whether the Pharmacy anomaly creates an SLA risk.

The SLA result becomes part of the structured downstream evidence.

---

## 11. RAG Handoff

The Pharmacy pipeline passes structured JSON to RAG.

The JSON represents observed evidence generated by the pipeline.

RAG uses:

- Pharmacy evidence
- Pharmacy Knowledge Base
- Common Healthcare Knowledge Base
- Relevant remediation procedures
- Relevant troubleshooting information

to generate the RCA and recommendation.

---

## 12. Expected RAG Evidence

Important Pharmacy evidence may include:

- Dataset
- Record ID
- Rule violations
- ML evidence
- Contributing features
- Record context
- Anomaly correlation
- Severity
- Risk
- SLA information

---

## 13. Example Interpretation

Observed evidence:

Duplicate rate increased significantly.

RAG should not treat the ML model's observation as the root cause.

Instead:

Observed Evidence
    ↓
Knowledge Base Matching
    ↓
Known Anomaly Pattern
    ↓
Possible Root Cause
    ↓
Resolution Procedure
    ↓
Recommendation

---

## 14. Important Principle

The Pharmacy ML model provides evidence.

The Pharmacy Knowledge Base provides Pharmacy-specific domain knowledge.

The Common Healthcare Knowledge Base provides generic data-quality knowledge.

RAG combines these sources to produce the final explanation and recommendation.
